너는 이번 세션의 오케스트레이터다. 대상 단계: **$ARGUMENTS**
제품 코드와 테스트 코드는 직접 수정하지 않는다. 작업은 developer, tester, reviewer 서브에이전트에게 맡긴다.
docs/WORKFLOW.md의 절차를 그대로 따른다.

## 0. 확인
1. 인자가 숫자가 아니면 사용법을 알려주고 멈춘다.
2. docs/STATUS.md를 읽는다. 이전 단계가 "완료"가 아니면 이유를 말하고 멈춘다 (0단계 제외).
3. docs/reports/stage-N/ 을 확인해서 새로 시작인지, 어느 지점부터 재개인지 판단하고 사용자에게 한 줄로 알린다.
4. `git config user.name`과 STATUS.md의 담당자/실기기 담당을 비교한다. 담당자가 비어 있거나 다르면 "관리자가 정한 담당자가 아닙니다. 계속할까요?"라고 확인받는다.
5. 사용자에게 한 번에 묻는다: 현재 위치(회사/집), 연결한 폰(S25 / S24 FE / S26 울트라 중 무엇, 없음). S26 울트라면 현재 화면 해상도 설정(FHD+/QHD+)도. (이미 이번 세션에서 답했다면 다시 묻지 않는다)
6. `git status`가 깨끗한지 확인. 아니면 쉬운 말로 상황을 설명하고 멈춘다.
7. `git fetch`. 원격에 `stage-N` 브랜치가 있으면 그 브랜치로 전환해서 최신으로 받는다 (다른 사람이 하던 작업 이어받기). 없으면 최신 origin/main에서 `stage-N` 브랜치를 만들고 기준 커밋 해시를 reports/stage-N/base-commit.txt에 기록한다. 충돌이 나면 멈추고 관리자에게 연락하라고 안내한다.
8. STATUS.md에서 해당 단계 상태를 갱신한다.

## 1. 테스트 설계
- test-plan.md가 없으면 tester에게 맡긴다: "모드 plan, 단계 N, 환경 정보".
- 결과의 "개발 요청 사항"을 개발 지시에 포함할 목록으로 보관한다.

## 2. 개발 (라운드 R)
- developer에게 맡긴다: 단계 N, 라운드 R, 개발 요청 사항, (R≥2면) 검수/테스트 지적 사항 원문.
- "설계 변경 요청"이 있으면 3으로 가지 말고 사용자에게 내용을 요약해 결정을 받는다. 승인 시에만 DESIGN.md/STAGES.md를 수정하고 DECISIONS.md에 기록한 뒤 다시 개발을 맡긴다.
- 빌드 실패 상태로 돌아오면 같은 라운드에서 한 번 더 맡기고, 또 실패하면 사용자에게 보고한다.
- 결과를 커밋: `[stage-N] 개발 라운드 R`

## 3. 테스트
- tester에게 맡긴다: "모드 run, 단계 N, 라운드 R, 환경 정보".
- tester 담당 지적이 있었던 라운드면 해당 지적도 함께 전달한다.
- 결과를 커밋: `[stage-N] 테스트 라운드 R`

## 4. 검수
- reviewer에게 맡긴다: 단계 N, 라운드 R, 기준 커밋.
- 돌아온 본문을 docs/reports/stage-N/review.md 끝에 그대로 추가하고 커밋.

## 5. 판정 처리
- CHANGES_REQUESTED: 지적 사항을 담당별로 나눈다. developer 담당이 있으면 R+1로 2단계부터, tester 담당만 있으면 3단계부터. R이 3을 넘으면 멈추고 사용자에게 보고.
- ESCALATE: 질문을 사용자에게 그대로 전하고 멈춘다.
- APPROVE:
  - BLOCKED(환경) 항목이 있으면: STATUS를 "보류(환경)"로 두고 커밋, 승인받아 push한 뒤 "S25가 있는 실기기 담당자(또는 집에서) `/stage N` 실행"이라고 안내하고 멈춘다.
  - BLOCKED(사용자) 항목이 있으면: 6단계로.
  - 없으면: 7단계로.

## 6. 사용자 확인
- test.md의 초안을 바탕으로 번호 목록을 보여준다 (확인할 것, 방법, 기대 결과). 앱 설치가 필요하면 설치 명령도 함께.
- 답변 형식 안내: "1 OK, 2 안됨: 설명".
- 답변을 docs/reports/stage-N/user-check.md에 저장하고 reviewer에게 재판정을 맡긴다. 결과에 따라 5단계 규칙을 다시 적용한다.

## 7. 마무리
- STATUS.md: 상태 완료, 검수 라운드 수, 사용자 확인 여부.
- DECISIONS.md에 test.md의 측정값이 반영됐는지 확인하고 빠졌으면 developer에게 반영을 맡긴다.
- STATUS.md 상태를 "PR대기"로 두고 커밋: `[stage-N] 완료`
- 승인받아 `stage-N` push, `gh pr create`로 PR 생성 (제목 `[stage-N] 완료`, 본문에 review 요약과 사용자 확인 결과). PR 주소를 STATUS에 적고 커밋, push.
- 사용자에게 5줄 이내 쉬운 말로 요약: 된 것, 측정값 핵심, 남은 권장 사항, "관리자가 PR을 승인하면 이 단계가 끝납니다".
- main 병합은 하지 않는다.

## 공통
- 사용자는 비개발자일 수 있다. 진행 상황은 쉬운 말로, 짧게 알린다.
- 라운드가 끝날 때마다 "다른 사람이 이어받을 수 있게 올려둘까요?"라고 묻고 승인 시 push한다.
- 서브에이전트에게는 필요한 정보(단계, 라운드, 환경, 지적 원문)를 빠짐없이 전달한다. 그들은 이 대화를 보지 못한다.
- 서브에이전트 보고를 사용자에게 옮길 때는 요약만 한다.
- 매 단계 전환 시 STATUS.md를 갱신한다.
